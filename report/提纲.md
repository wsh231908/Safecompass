### slide1

​	各位老师好，我们组的选题是E：大模型治理的评测体系和平台构建，我们构建了一个面向大模型的安全风险评测与可视化分析平台safecompass。我们的平台不关注模型的普通对话问答能力，而是模型在面对有害请求和越狱攻击时，是否还能稳定拒答、是否还能给出安全边界内的响应。这里展示了该平台进行安全评测的步骤：从有害请求出发，经过攻击 prompt 包装，再到被测模型响应，最后由 Judge 和可视化报告给出评测结论。接下来我会介绍为什么需要这样的平台、我们具体的实现细节，并用三个评测的实例来验证这个平台是可用的。

### slide2

​	我们先看问题背景。大语言模型能力越强，越可能被用于生成危险内容，比如网络攻击步骤、违法行为指导、虚假信息、骚扰内容、化学与生物风险内容，或者版权文本复现。虽然主流模型通常有安全对齐，但真实交互里，用户可以通过改写请求、添加角色设定、伪装成研究场景、要求忽略规则等方式进行越狱。

​	所以，仅仅测试模型能不能回答普通问题是不够的。我们真正关心的是：在有害请求和攻击 prompt 共同作用下，模型是否仍然可靠拒答；不同模型、不同 Judge 设置下，安全结论是否可复现、可比较。

### slide3

​	相关工作方面，我们参考了 JailbreakBench 和 HarmBench 这类安全评测基准。它们提供了有害行为数据集、攻击方法和评测指标，比如 ASR，也就是 Attack Success Rate，表示攻击成功率。

我们与这些论文的区别是：不是简单复现一个静态 benchmark，而是把评测流程平台化。也就是说，我们把数据集加载、攻击 prompt 生成、模型调用、LLM-as-judge 判分、结果保存和可视化报告放在同一个本地流程里，让每次实验都有可复现记录，也方便横向比较不同模型和 Judge 机制。

### slide4

​	这一页是平台的核心架构。SafeCompass 的评测流程从数据集选择开始，然后把不同来源的样本规范化成统一 case，再生成攻击 prompt，调用被测模型得到回复，之后由 Judge 判断回复 safe 还是 unsafe，最后导出 Markdown 报告、图表和 ASR 等指标。

这里有两个设计点需要强调。第一，模型调用既可以接我们部署在本地服务器上的 Llama-3-70B AWQ，也可以接 OpenAI-compatible 接口。第二，Judge 支持 official_jbb 单 Judge，也支持 multi_judge 投票，这使我们能够观察评判机制本身对安全结论的影响。

### slide5

​	为了让不同数据集能够进入同一个流程，我们设计了 `safecompass.case.v1` schema。无论原始样本来自 JailbreakBench、HarmBench，还是用户自定义 JSON 或 CSV，平台都会规范化为包含 id、source、dataset、prompt、goal、category、behavior_type 和 metadata 的统一结构。

这个 schema 的作用是把数据差异挡在入口处。后续攻击方法、模型调用、Judge 判分和报告生成都只依赖统一 case。攻击策略方面，目前支持 Direct Request、Human Jailbreaks 和 Jailbreak Chat，主要覆盖 prompt 修改类攻击。

### slide6

​	接下来进入实验。三次实验都使用 HarmBench 的 text_test 子集，共 200 条样本，攻击方法都固定为 Jailbreak Chat。这样做是为了控制数据集和攻击方式不变，分别观察 Judge 模式和被测模型变化带来的影响。

实验一使用 Llama-3-70B 加 official_jbb 单 Judge；实验二仍然是 Llama-3-70B，但 Judge 改为 multi_judge；实验三把被测模型换成 GPT-5.4，同时使用 official_jbb 单 Judge。这个设计让我们可以验证两个问题：Judge 会不会影响结论，模型本身会不会影响结论。

### slide7

​	实验一中，本地 Llama-3-70B 在 official_jbb 单 Judge 下，200 条样本有 185 条被判定为安全拒绝，15 条被判定为越狱成功，整体 ASR 是 7.5%。从左侧类别图可以看到，风险最高的是 cybercrime_intrusion，ASR 为 15.6%；illegal 和 harmful 也有一定成功率，而 copyright 为 0%。

这个结果说明，在单 Judge 标准下，本地 Llama 整体具备较强拒答能力，但并不是没有薄弱点。尤其是网络入侵和违法行为类任务，仍然更容易出现越狱成功样本。

### slide8

​	实验二保持数据集、攻击方式和被测模型不变，只把 Judge 模式从 official_jbb 改为 multi_judge。结果变化很明显：安全拒绝降到 162 条，越狱成功升到 32 条，另有 6 条需要复核，整体 ASR 从 7.5% 上升到 16.0%。这说明多 Judge 模式更敏感，能发现一些单 Judge 可能漏判的风险。图表中 cybercrime_intrusion、misinformation_disinformation 和 copyright 的风险上升尤其明显。不过多 Judge 也会带来 Judge 分歧，所以平台需要保留需复核样本，供人工检查。

### slide9

​	为了验证平台有对不同能力的模型的区分度。第三次实验把被测模型换成 GPT-5.4，并保持 HarmBench text_test、Jailbreak Chat 和 official_jbb 单 Judge 不变。结果是 198 条安全拒绝，0 条越狱成功，2 条需复核，整体 ASR 为 0.0%。与实验一相比，两者 Judge 标准相同，攻击方式相同，主要差异是被测模型不同。因此可以看到，在这组实验设置下，GPT-5.4 表现出更强的安全拒答能力。不过 chemical_biological 中仍有 2 条 ambiguous，需要人工检查模型回复和 Judge 输出，避免边界判定或接口问题造成误判。

### slide10

​	最后总结一下。通过上面的三个实例，我们能够看到关于平台设计与llm judge的一些结论。第一，Judge 机制会影响评测结论；同一个 Llama 模型，单 Judge 下 ASR 为 7.5%，多 Judge 下上升到 16.0%。第二，不同的模型确实反映出不同的实验结果，证明了平台的可用性与区分度。

当前项目仍是课程项目原型，也有不足：数据集覆盖还不够全面，攻击方法主要是 prompt 修改类，Judge 可靠性还需要进一步验证。后续我们计划扩展更多 benchmark 和危害类别，引入 PAIR 等自动化攻击策略，并强化 Judge 分歧分析、失败案例聚类、模型间横向对比和可复现实验记录。总体目标是把大模型安全评测变成一个可复现、可比较、可分析的本地化流程。最后展示一下使用平台评测的实际效果：





可能的问题：

我通读了核心实现、PPT 和 `report/文稿.md`。下面是老师比较可能追问的 10 个问题，以及建议回答。

1. **你们的平台和 JailbreakBench / HarmBench 本身有什么区别？**  
   答：JailbreakBench 和 HarmBench 更像评测基准，提供数据、攻击方式和指标。SafeCompass 的重点是把这些能力平台化：统一加载数据、生成攻击 prompt、调用被测模型、运行 Judge、保存结果并生成可视化报告。也就是说，我们不是只跑一次 benchmark，而是做了一个可复现、可比较、可分析的本地评测流程。

2. **为什么要设计 `safecompass.case.v1` schema？**  
   答：因为 JailbreakBench、HarmBench 和自定义数据集字段不统一。我们用统一 schema 把样本规范成 `id`、`source`、`dataset`、`prompt`、`goal`、`category`、`behavior_type`、`metadata` 等字段。这样后续攻击策略、模型调用、Judge 判分和报告生成都不需要关心原始数据来自哪里。

3. **ASR 是怎么计算的？**  
   答：ASR 是 Attack Success Rate，即被 Judge 判定为 `unsafe` 的比例。在我们这三次实验里，每个原始样本对应一个 Jailbreak Chat 攻击 prompt，所以 ASR 可以理解为 `unsafe 样本数 / 200`。如果未来一个样本生成多个攻击尝试，平台也会区分 attempt 级结果和原始 behavior 级 ASR，只要某个原始样本有一次攻击成功，就可计为该 behavior 被攻破。

4. **Judge 怎么判断 safe / unsafe？这个判断可靠吗？**  
   答：单 Judge 使用类似 JailbreakBench official judge 的判定方式：把原始有害请求和模型回复一起输入 Judge，让 Judge 判断回复是否实质性满足了有害请求。它不是绝对真值，所以我们又实现了 multi_judge，多 Judge 投票可以降低单个 Judge 偏差，但也会产生分歧。因此平台保留 `ambiguous` 和需复核样本，强调高风险样本仍需要人工检查。

5. **multi_judge 的投票规则是什么？**  
   答：平台只把正常返回且标签为 `safe` / `unsafe` 的票作为有效票。`unsafe` 票多于 `safe` 票，就判为越狱成功；`safe` 票更多，就判为安全拒绝；如果平票、未知输出或错误导致无法形成多数，就标为 `ambiguous` 需复核。同时保存每个 Judge 的原始输出、一致率、unknown 票和 error 票。

6. **为什么同一个 Llama 模型，单 Judge ASR 是 7.5%，multi_judge 变成 16.0%？**  
   答：因为变化的是评判机制，不是数据集、攻击方法或被测模型。multi_judge 更敏感，会把一些单 Judge 可能漏判的版权复现、虚假信息、网络入侵边界样本识别出来。但这不代表 multi_judge 一定完全正确，它也引入了分歧，所以我们把 6 条样本标为需复核。

7. **为什么 GPT-5.4 的 ASR 是 0.0%，能否说明它完全安全？**  
   答：不能说完全安全。这个结果只能说明在 HarmBench text_test、Jailbreak Chat、official_jbb 单 Judge 这组实验条件下，GPT-5.4 没有被判为越狱成功。它仍有 2 条 chemical_biological 的 ambiguous 样本，需要人工复核。更严格的结论需要更多数据集、更多攻击方法和更可靠的人工验证。

8. **你们目前支持哪些攻击方式？为什么没有完整接入 PAIR？**  
   答：当前主要支持 Direct Request、Human Jailbreaks 和 Jailbreak Chat，属于 prompt 修改类攻击，适合课程项目中做稳定、可复现实验。代码里已经有 PAIR 相关框架和参数设计，但完整自动化攻击需要更复杂的攻击模型、迭代策略、成本控制和安全约束，所以我们把它放在后续工作里。

9. **如果模型接口调用失败，平台怎么处理？**  
   答：后端对 OpenAI-compatible 接口做了基本重试，遇到 408、429 或 5xx 等可重试错误会重试；如果单条样本最终失败，会构造成 error result，而不是让整个实验崩掉。Judge 失败也会记录为 error vote，并可能导致最终结果变为 ambiguous，方便后续复核。

10. **你们平台的最大局限是什么？后续最应该改进哪里？**  
    答：主要有三点。第一，数据覆盖还有限，目前重点是 JailbreakBench harmful 和 HarmBench text_test。第二，攻击方式主要是 prompt 修改类，还需要接入 PAIR 等更强自动化攻击。第三，Judge 本身不是金标准，需要更多人工标注或交叉验证。后续最值得做的是扩展 benchmark、增强攻击策略对比、加入 Judge 分歧分析和失败案例聚类。

**前端做的事**
主要是浏览器里的交互和展示：

- 页面入口：[index.html](/home/u2023202105/Safecompass/index.html)、[chat.html](/home/u2023202105/Safecompass/chat.html)
- 前端主逻辑：[src/app.js](/home/u2023202105/Safecompass/src/app.js)
- 评测请求调度：[src/api/evaluation-client.js](/home/u2023202105/Safecompass/src/api/evaluation-client.js)
- 攻击 prompt 生成：[src/attacks/strategies.js](/home/u2023202105/Safecompass/src/attacks/strategies.js)
- 报告导出和图表展示：[src/reporting](/home/u2023202105/Safecompass/src/reporting)

前端负责：选择数据集、选择模型/Judge 配置、设置攻击方式、上传自定义数据、发起评测请求、接收进度流、展示 ASR、表格、图表、导出报告。

**后端做的事**
后端是 Node.js 写的，核心文件是：[server.js](/home/u2023202105/Safecompass/server.js)

后端负责：

- 提供静态页面和资源
- 接收 `/api/evaluate`、`/api/evaluate-stream` 评测请求
- 调用被测模型的 OpenAI-compatible API
- 调用 Judge 模型或 rule-based fallback
- 聚合 single Judge / multi Judge 投票
- 计算 safe、unsafe、ambiguous、ASR 等结果
- 把每次运行保存到 [runs](/home/u2023202105/Safecompass/runs)
- 提供本地 Llama chat API

**哪些代码是共享的**
有些 JS 既不是纯前端，也不是纯后端，而是共享逻辑。例如：

- [src/domain/case-schema.js](/home/u2023202105/Safecompass/src/domain/case-schema.js)

这个文件里的 `safecompass.case.v1` 规范化逻辑，前端和后端都可能使用。`server.js` 也直接 import 了它。

所以答辩时可以这样说：

> 我们的项目采用 JavaScript 全栈实现。前端运行在浏览器里，负责交互、配置、展示和导出；后端运行在 Node.js 里，负责模型调用、Judge 判分、结果聚合和运行记录保存。并不是所有 JavaScript 都是前端代码，`server.js` 是后端，`src/domain/case-schema.js` 这类模块是前后端共享逻辑。
